# 502 与登录恢复验收（2026-11-12）

## 证据与修改

- 06:37 UTC 自动安全更新升级 MySQL，systemd 因 API 的 Requires 依赖停止 API；数据库恢复后 API 未恢复。API 正常退出，不触发 Restart=on-failure；本次无 OOM 证据。
- 已恢复 API，将基础服务文件的 MySQL/Redis 强依赖改为 Wants，保留 After 启动顺序及安全更新。
- 路由原先把任何 getInfo/菜单加载失败当作会话失效并注销；现在仅明确 401 才注销。502/503/504、403、网络中断进入恢复页并保留凭据；重试重新加载身份与菜单。
- Cookie 会话探测失败同样进入恢复页，不误跳登录。
- 发现发布切换时旧页面引用已移除的资源，导致登录后路由加载卡住；新版本保留上一版静态资源，首页缓存需重新验证，缺失静态文件返回 404。
- 未延长登录有效期，未关闭安全更新，未升级实例，未迁移业务数据。

## 验证

- 新增故障回归先失败（7 失败/3 通过），修复后定向 11 项通过。
- 前端完整测试 109 文件、1413 项通过；类型检查、生产构建通过。
- 隔离 systemd 测试：停止模拟依赖，Requires 服务变 inactive，Wants 服务保持 active。没有重启生产数据库来测试。
- 实际 API Requires 已无 mysql/redis，Wants 包含两者；本地及公网 captchaImage 均 200。
- gstack 线上真实账号登录通过；在当前验收浏览器中模拟 getInfo 502（未使真实服务停机），恢复页展示且凭据保留；恢复真实接口后点击重试，无需重新登录进入广告账户页，角色成功加载。
- 首页响应 Cache-Control:no-cache；上一版懒加载 JS 可读。前端部署为 20261112-session-resilience，API 仍用原 launch-config 代码。

## 边界

本次证明临时错误不会被误判为退出，及依赖维护不再永久停掉 API；不宣称消除所有潜在 502。数据库维护期间仍可能短暂不可用。正常空闲/绝对到期、主动注销、权限撤销仍遵循原会话策略。长期稳定性需要运行观察。
