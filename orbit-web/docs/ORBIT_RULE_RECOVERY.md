# 规则未知请求同主体恢复

本节点只接已有六动作的只读恢复身份，不增加写接口。初次 SAVE、SCOPE、ACTION 发出之前实际 GET `/rules/recovery-context?action=...`，原生 actor_id 与当前 user.id 必须相同；保存规范 tenant_id 和 actor_id 作为客户端旁证，不加入原业务正文。

页面提供在新标签页打开 `/login`（`target=_blank rel=noopener`）。原页与父内存必须保留；未确认意图阻止 SPA 离开，不承诺硬刷新或浏览器重启恢复，不使用 Storage 保存业务事实。OIDC 完整跳转在另一页执行。

回原页后点击“重新验证当前身份（不提交）”，实际恢复 GET →现有尊重 Cookie/Bearer 的 getInfo→再次恢复 GET。只有两次都与原 actor/tenant 相符且刷新后的原生用户相符，才重新绑定客户端 UI 上下文。此步骤不 POST，也不能证明具体 Rule 仍可见。

随后再次显式点击原组件恢复按钮：再次 GET 同主体证明，Cookie 模式仅更新当前传输 CSRF；重发原正文、幂等 key、quoted If-Match。具体对象范围与成功键重放仍由原动作服务端授权。与原主体不同、撤权或读取失败均保留原未知，不披露旧名称/原因、不自动重发。503 不作为撤权。

两步流程不以 lifecycle nonce 充当授权。首次身份捕获失败且尚未发送不生成假未知意图；已经发送后即使恢复遭403/409，也不能推断原请求未受理。

本节点定向测试使用 fetch/组件替身，不能计真实登录、OIDC、HTTP或浏览器通过。主线需实际验证新标签再认证、同主体恢复、异主体拒绝、Cookie CSRF 更新与原成功回执。默认无服务启动、无平台请求。
