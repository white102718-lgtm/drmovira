# 成效推送

用于新增 Doris 成效定时推送。

1. 单时点日报可在 `ad_daily_detail` 的 ad 级数据上先过滤再汇总；需要回溯多个执行节点时，必须使用 `ad_hourly_detail.china_date` 的小时明细累计，不能用会被后续刷新覆盖的日表。
2. 根据展示需求直接按代理线聚合，或用 `fb_ad_channel.account_ids_json` 的账户映射后按渠道聚合；不要混用两种维度。
3. 成本一律由聚合后的总消耗除以聚合后的转化人数计算，分母为 0 时展示 `-`；汇总行必须按汇总后的指标重新计算成本。
4. 将任务注册到 `tasks/main.py`，明确 APScheduler 的 `Asia/Shanghai` 时区和跨日取数规则。
5. 图片报表须使用支持中文的字体，并通过飞书应用先上传图片取得 `image_key` 后发送。
6. 若同图比较当前、上个节点、昨日同期和昨日上个节点，12:00 的当前/昨日同期按巴西 UTC-3 的完整前一日取数；后续节点引用 12:00 时必须取该节点的小时累计快照，而非全天复核值。
7. 测试群若使用签名 Webhook，图片仍需先由飞书应用上传取得 `image_key`，再以 `timestamp`、`sign` 和 `msg_type=image` 调用 Webhook；生产群继续通过应用消息 API 发送。发送函数应以显式参数区分测试和生产目标。
8. “消耗加速度”图的纵轴是消耗增长率百分比，不是美元：今日增长率 `(当前消耗 - 上个时段消耗) / 上个时段消耗`，昨日增长率 `(昨日同时段消耗 - 昨日上个时段消耗) / 昨日上个时段消耗`；图上只展示昨日、今日两个点，加速度为两者相减的百分点。分母为 0 时显示无可比较数据。
9. `ad_hourly_detail` 的小时行是“截至该时点的当天累计快照”，不是小时增量。多时段查询必须先按“时段 + 广告唯一键”选 `china_date` 最新行（例如 `ROW_NUMBER() = 1`），再按代理线求和；绝不能直接求时段内所有小时行的和。
10. 北京时间普通整点报取执行时已经完成的前一小时快照（例如 09:00 报取到 08:00）；12:00 全天复核以 `< 12:00` 包含最终 11:00 快照。供 15:00 等后续时报引用的“12 点时点数据”则单独取新巴西日的 12:00 小时快照，不能混用全天复核。
11. 顶部项目趋势图与明细表使用相同的展示代理线范围：先按明细表“当前注册和首充不同时为 0”的规则确定代理线，再在顶部按巴西 UTC-3 的 0、3、6…固定整点取这些代理线的累计快照。趋势横轴始终完整展示 0—24，尚未到达的点留空；00:00 固定展示为零基线，不能读取可能残留前一广告日累计的小时行；实际查询起点仍是与明细一致的巴西 01:00。任务在北京时间 `:30` 触发，只展示已经完成的上一个巴西三小时时点（如北京时间 03:30 展示到巴西 15:00）。12 点任务的趋势图展示刚结束巴西自然日的 0—24 点；近 3 小时柱状消耗由相邻小时累计值相减，较昨日同期为 `((A-B)-(C-D))/(C-D)*100`。
12. 项目范围由 `GAME_PLATFORMS` 集中维护；所有 SQL 的 `game_platform IN (...)` 都从该元组生成，新增项目后会按项目分别渲染并发送一张图片。
13. 手动调试允许任意北京时间：先通过 `_current_schedule_slot` 将当前时刻归位到最近已完成的计划节点（如 17:00 归位为 15:00，05:00 归位为 03:00），再用 `_previous_schedule_slot` 取得其前一个节点（分别为 12:00、00:00）。表格、标题和顶部图表必须共用这个归位后的当前节点；正式调度仍按配置节点触发。
14. 图 1、2 的数值不要覆盖在折线点附近：在固定横轴下方依次展示时间、今日值（蓝色）、昨日值（黄色），未来空时段只保留时间刻度。
15. 全天趋势图的横轴下方消耗金额应使用紧凑 `k` 单位（如 `202.7k`），避免九个固定时点的长金额文字重叠；成本仍保留两位小数。
16. 当横轴下方有三行文字时，三张顶部图表卡片必须统一增高并同步下移表格，确保数值与卡片底边留有视觉间距。
