# 工作台任务中心：素材均衡分配、投放去重与超送设计

> 文档状态：前端阶段已实现（V0.2）  
> 编制日期：2026-09-03  
> 影响范围：工作台 / 任务中心、素材工单、素材交付、广告创建、项目成员  
> 本期目标：按本文规则完成任务中心前端闭环，并明确后端硬约束的实施边界

## 0. 实施状态

当前已完成任务中心前端阶段：素材任务与投放任务拆分为两个独立 Tab；素材任务的分配入口按子需求逐条选择素材师，再在该子需求选定人员中均分生产名额，同时支持子需求和素材排序、锁定项保护及同项目超送预览；投放任务支持按执行单元分配素材、默认禁止重复、素材不足阻断以及显式循环复用。确认结果已纳入任务中心本地状态并带版本和确认时间。新建素材任务新增“个人任务 / 部门任务”归属，任务中心保存完整需求快照并在统一详情中展示全部字段；旧需求验收页面代码已删除，素材查看与验收统一进入任务中心，历史链接仅保留安全重定向。

仍需后端配合才能形成生产环境硬约束：正式项目成员关系、稳定素材师 ID 与生产名额交付绑定、分配批次接口、乐观锁和唯一约束、广告发布按分配项取材、幂等与审计台账。前端目前只从同项目任务的稳定参与人记录构建兼容成员集合；无法确认项目关系的人员不会进入超送接收列表。

## 1. 背景与结论

当前任务中心已经能把一个任务分给多人，但“子需求—素材师—素材—投放执行单元”之间没有逐项分配关系：多人看到的是同一组任务级素材，素材交付也只记录一次上传所选的素材师和子需求。因此系统无法证明素材师是否均匀承接，也无法阻止多个投放执行单元重复使用同一素材。

同时，现有“超出需求”只是一条数量提示。系统没有超送素材池、项目成员范围校验、接收人分配、撤回和审计能力。

本设计建议引入两层分配：

1. **生产分配**：把每个子需求拆成有顺序的生产名额，按轮转规则均匀分给素材师。
2. **投放分配**：把已验收素材逐一绑定到具体投放执行单元；默认不重复，素材不足时阻断确认。

超出子需求计划数量的素材进入**超送池**，只能分配给同项目的有效成员。超送默认采用“一份素材、一个接收人”的独占分配，避免与投放去重目标冲突。

## 2. 目标与非目标

### 2.1 目标

- 子需求具有稳定、可持久化的排列顺序。
- 相同能力和容量条件下，素材师承接数量尽可能均匀。
- 分配结果可预览、可确认、可追踪；重算不破坏已交付或已使用的记录。
- 多个投放人员、账户、广告组或广告位不会隐式拿到同一素材版本。
- 超送素材仅流转给同项目有效成员，并保留完整审计记录。
- 并发操作、重复提交和接口重试不会产生重复分配。

### 2.2 非目标

- 本期不设计素材推荐、素材效果预测或智能标签模型。
- 本期不改变素材文件的底层存储方式。
- 本期不把“均匀”扩展为按工时、难度或历史绩效自动计费；这些能力只预留权重字段。
- 本期不自动修改已发布广告使用的素材。

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 素材工单 | 一个项目下的素材生产与交付任务。 |
| 子需求 | 素材工单中的一条需求明细，包含数量、时长、说明等。 |

## 5. 总体流程

```mermaid
flowchart LR
  A[素材工单及有序子需求] --> B[生成生产名额]
  B --> C[素材师均衡分配预览]
  C --> D[确认并锁定生产分配]
  D --> E[按生产名额交付与验收]
  E --> F{是否超过计划数量}
  F -- 否 --> G[可投放素材池]
  F -- 是 --> H[同项目超送池]
  G --> I[投放执行单元去重分配]
  H --> J[同项目成员独占分配]
  I --> K[广告创建按明确绑定提交]
  J --> G
```

核心原则如下：

- **先计划、后交付、再分发**：不再依赖任务级共享数组隐式推断归属。
- **前端预览，后端裁决**：均衡算法可在前端展示，但唯一性、项目归属和并发版本必须由后端校验。
- **使用稳定 ID**：用户、子需求、素材版本、投放执行单元均使用稳定 ID；名称只作为快照展示。
- **已锁定事实不可重算**：已交付、已验收或已投放的关系不被自动重排，只重算剩余名额。

## 6. 详细业务设计

### 6.1 子需求排序

每个子需求新增：

- `sort_order`：从 1000 起按 1000 递增，便于局部插入。
- `row_version`：乐观锁版本。
- `status`：`active`、`cancelled`。

规则：

1. 工单详情和任务中心始终按 `sort_order ASC, id ASC` 展示。
2. 拖拽排序后一次性提交完整顺序；后端在事务内规范化并递增工单版本。
3. 已生成生产分配后仍可改顺序，但只影响展示和未锁定名额的下一次重算，不改变已锁定分配。
4. `seq_label` 继续作为展示快照兼容旧数据，不再作为真实排序依据。
5. 旧工单首次读取时按现有数组顺序回填 `sort_order`。

### 6.2 素材师均衡分配

#### 6.2.1 输入

- 按稳定顺序排列的有效子需求。
- 每条子需求的计划数量 `planned_quantity`。
- 每条子需求单独选定的素材师范围，以及人员的 `designer_user_id`、显示名、是否有效、容量权重。
- 已锁定的生产名额。

#### 6.2.2 默认算法（P0）

1. 分配入口逐条展示子需求；每条子需求必须独立选择一位或多位素材师，不能用整单人员选择替代。
2. 每条子需求按计划数量生成生产名额，例如数量 3 生成 `1/3、2/3、3/3`。
3. 排除已取消人员；保留其已交付/已验收名额，释放尚未开工名额。
4. 对未锁定名额只在当前子需求选定的素材师范围内执行连续轮转。
5. 同一轮中以 `当前总名额数 ASC、用户优先级 ASC、用户 ID ASC` 决定下一位。
6. 确认后生成分配批次；再次点击确认必须携带工单版本和幂等键。

在所有素材师容量相同且没有锁定历史时，应满足：

- 任意两位素材师的工单总名额数差值不超过 1。
- 对任一子需求，任意两位素材师的名额数差值不超过 1。

容量权重在 P1 启用。届时按 `已分配数 / capacity_weight` 选择负载最低者；默认权重为 1。

#### 6.2.3 重算与人工调整

- `planned` 名额允许拖动给其他素材师。
- 已上传素材的名额进入 `delivered`，不得自动换人。
- 已验收名额进入 `accepted`，只有管理员执行“作废分配”后才能重新分配。
- 人工调整导致差值大于 1 时允许保存，但必须填写原因并产生审计记录。
- 减少子需求数量时，优先取消未开始且序号靠后的名额；不得静默删除已交付名额，超出部分转入超送候选池。

### 6.3 素材交付绑定

交付时不再只提交“素材师名称 + 子需求 ID”，而应提交 `production_slot_id` 和 `designer_user_id`。

#### 6.3.1 素材排列顺序

- 每个素材版本增加持久化的 `material_sort_order`，并在所属子需求内唯一排序。
- 默认顺序继承生产名额的 `slot_no`；同一名额存在多个历史版本时，只展示当前有效版本，历史版本不参与排序。
- 验收后可在“素材分配”页签拖拽调整素材顺序，后端使用版本号原子保存。
- 投放自动分配严格按该顺序取材，禁止依赖接口返回顺序、文件名或前端数组下标。
- 排序变化只影响尚未锁定的投放执行单元；已预留、发布中或已使用的素材归属不变。
- 超送素材保留原子需求顺序，并在同序时按验收时间、素材版本 ID 排列。

#### 6.3.2 交付规则

规则：

- 素材师本人上传时，系统自动带出其未完成名额。
- 管理者代传时可选择素材师，但提交稳定用户 ID，并保存姓名快照。
- 一个生产名额默认只绑定一个当前素材版本；重新上传形成新版本，不复用旧版本 ID。
- 一个上传批次可包含多个文件，但每个文件必须分别绑定生产名额；不能让整批文件共享一个模糊归属。
- 验收通过后才进入可投放素材池；驳回版本不参与均衡和投放分配。

### 6.4 多投放去重

#### 6.4.1 投放执行单元

系统先展开待创建广告的全部投放执行单元，每个单元生成稳定键：

`project_id + delivery_task_id + executor_user_id + platform + account_id + campaign_id + adset_id + slot_no`

尚未具备 campaign/adset ID 时使用创建草稿 ID，正式创建成功后回写真实 ID。

#### 6.4.2 默认去重规则

1. 只使用已验收且当前成员有权限的素材版本。
2. 素材按 `material_sort_order ASC, accepted_at ASC, material_version_id ASC` 排序。
3. 投放执行单元按任务、人员、账户、广告组、广告位的稳定键排序。
4. 在“同一项目 + 同一素材工单 + 活跃分配周期”内，一个素材版本最多分给一个投放执行单元。
5. 素材数不少于执行单元数时，一一匹配，不产生重复。
6. 素材数少于执行单元数时默认阻断确认，提示缺少数量和未分配执行单元。
7. 具有高级权限的用户可以开启“允许循环复用”。复用必须在全部可用素材至少使用一次之后发生，并填写原因；所有重复项在预览中明确标红。
8. 已进入发布中的分配被锁定；失败重试沿用原分配和幂等键，不重新抽取素材。

#### 6.4.3 与广告创建的衔接

广告创建接口不得再接收一组未绑定位置的顶层素材并按索引猜测归属，而应接收确认后的 `distribution_items`。每个广告对象都带有准确的素材版本、任务、人员、账户、广告组和广告位。

若广告平台创建失败：

- 可重试错误：保留素材占用，使用同一幂等键重试。
- 确认失败且取消发布：释放未实际使用的分配。
- 已创建成功：写入使用台账，不允许普通用户重新分配该素材版本。

### 6.5 超送同项目人员

#### 6.5.1 超送判定

超送应先按子需求判定，再汇总到工单：

`子需求超送数 = 已验收有效素材数 - 当前计划数量`

只有结果大于 0 的部分进入超送池。待验收、驳回、删除或被新版本替代的素材不计入。

#### 6.5.2 接收人范围

接收人必须同时满足：

- 是该工单 `project_id` 下的有效项目成员。
- 具有素材使用权限，且账号未禁用。
- 未被项目配置排除。

推荐建立正式的 `ProjectMember` 关系，至少包含 `project_id`、`user_id`、`role`、`status`、`joined_at`、`left_at`。在该关系上线前，不建议仅用姓名或当前任务参与人做硬校验。

#### 6.5.3 分配方式

- 默认方式：“同项目人员均分”。按接收人当前已获超送数从少到多轮转。
- 可切换“手动指定”。
- 默认一份超送素材只分给一个接收人；系统创建访问授权或引用，不复制物理文件。
- 接收人未实际使用前，管理员可撤回或转交；使用后记录锁定。
- 没有合格接收人时保留在未分配超送池，不自动发给跨项目人员。
- 超送转为投放素材时仍须经过投放去重检查。

### 6.6 状态模型

生产名额状态：

`planned → accepted_by_designer → in_progress → delivered → accepted`

异常分支：

- `planned / accepted_by_designer / in_progress → cancelled`
- `delivered → rejected → in_progress`
- `accepted → oversend_pool`（计划数量下降或额外交付时）

投放分配状态：

`preview → reserved → publishing → used`

异常分支：

- `preview → discarded`
- `reserved → released`
- `publishing → failed_retryable`（仍保留占用）
- `publishing → failed_final → released`

## 7. 数据模型建议

### 7.1 `material_requirement_item`

| 字段               | 说明            |
| ------------------ | --------------- |
| `id`               | 子需求稳定 ID。 |
| `order_id`         | 素材工单 ID。   |
| `planned_quantity` | 计划数量。      |
| `sort_order`       | 排列顺序。      |
| `row_version`      | 并发版本。      |
| `status`           | 有效或取消。    |

### 7.2 `material_production_slot`

| 字段                               | 说明               |
| ---------------------------------- | ------------------ |
| `id`                               | 生产名额 ID。      |
| `order_id` / `requirement_item_id` | 所属工单和子需求。 |
| `slot_no`                          | 子需求内序号。     |
| `designer_user_id`                 | 素材师稳定 ID。    |
| `designer_name_snapshot`           | 分配时姓名快照。   |
| `status`                           | 名额状态。         |
| `allocation_batch_id`              | 来源批次。         |
| `locked_at`                        | 锁定时间。         |

唯一约束：`(requirement_item_id, slot_no)`。

### 7.3 `material_version`

补充或规范以下字段：`production_slot_id`、`content_hash`、`material_sort_order`、`accepted_at`、`supersedes_version_id`。

`content_hash` 用于发现内容完全相同但版本 ID 不同的文件；P0 先警告，是否硬阻断作为后续策略。

### 7.4 `material_distribution_batch`

记录项目、素材工单、分配周期、状态、规则模式、是否允许复用、复用原因、工单版本、创建人、幂等键。

### 7.5 `material_distribution_item`

记录 `batch_id`、`material_version_id`、`execution_unit_key`、`recipient_user_id`、`purpose`（`required` / `oversend`）、`status` 和外部广告 ID。

关键约束：

- `(batch_id, execution_unit_key)` 唯一。
- 默认去重模式下 `(project_id, order_id, active_cycle, material_version_id)` 唯一。
- 所有确认、释放、撤回和复用动作写入审计表。

### 7.6 `project_member`

建立稳定的项目成员关系，作为超送授权和投放人员选择的统一数据源。姓名仅用于展示，所有权限判断使用 `user_id`。

## 8. 接口草案

接口名称为设计建议，最终路径可遵循现有后端规范。

### 8.1 子需求排序

`PUT /material-orders/{orderId}/requirements/order`

请求：

```json
{
  "order_version": 12,
  "items": [
    { "requirement_id": "req-2", "sort_order": 1000 },
    { "requirement_id": "req-1", "sort_order": 2000 }
  ]
}
```

版本冲突返回 `409` 和最新顺序，前端提示刷新后重试。

### 8.2 生产均衡预览与确认

- `POST /material-orders/{orderId}/production-allocation/preview`
- `POST /material-orders/{orderId}/production-allocation/confirm`

预览请求包含素材师稳定 ID、可选容量权重和工单版本；响应返回每个生产名额、每位素材师数量、最大差值、锁定项和告警。确认请求携带预览令牌与幂等键，后端必须重新校验版本。

### 8.3 素材交付

`POST /material-orders/{orderId}/deliver`

单个文件的关键字段：

```json
{
  "production_slot_id": "slot-101",
  "designer_user_id": "user-8",
  "requirement_id": "req-2",
  "material_version_id": "mat-ver-33",
  "file": { "basename": "...", "url": "..." }
}
```

兼容期允许旧字段 `designer`，但新流程必须提交 `designer_user_id` 和 `production_slot_id`。

### 8.4 投放去重预览与确认

- `POST /material-orders/{orderId}/distribution/preview`
- `POST /material-orders/{orderId}/distribution/confirm`
- `POST /material-distributions/{batchId}/release`

响应明确返回 `items`、素材缺口、重复项和不可用原因。确认时后端在同一事务内做唯一约束校验。

### 8.5 超送分配

- `GET /material-orders/{orderId}/oversend-pool`
- `POST /material-orders/{orderId}/oversend/preview`
- `POST /material-orders/{orderId}/oversend/confirm`
- `POST /material-distributions/{itemId}/revoke`

后端必须校验接收人在该项目中的有效成员关系；前端传入的项目 ID 和接收人范围不能作为可信依据。

## 9. 任务中心交互设计

素材工单任务详情增加“素材分配”页签，分四个区块：

1. **子需求顺序**：拖拽排序，展示计划数量、已交付、已验收和超送数。
2. **素材师负载**：矩阵展示子需求 × 素材师数量；提供“自动均分”“手动调整”“确认分配”。差值大于 1 时显示原因输入。
3. **投放分配**：左侧为投放执行单元，右侧为分配的素材缩略图；重复、缺口、无权限素材均有明确状态。
4. **超送池**：展示来源子需求、素材师、验收时间和接收人；提供“同项目人员均分”“手动指定”“撤回”。

交互要求：

- 自动分配只生成预览，用户确认后才写入正式关系。
- 确认前显示摘要：总名额、素材师人数、最大差值、投放位数、唯一素材数、缺口数、超送数。
- 已锁定项使用锁图标并说明原因；不允许无提示拖动。
- 项目成员、素材师或素材变化后，旧预览自动失效。
- 素材不足时，主按钮文案为“还缺 N 个素材”，默认不可确认。

## 10. 权限与审计

| 能力                | 建议权限主体                                  |
| ------------------- | --------------------------------------------- |
| 调整子需求顺序      | 工单创建人、项目 AM、管理员                   |
| 生成/确认素材师分配 | 项目 AM、素材负责人、管理员                   |
| 素材师接单与交付    | 对应生产名额的素材师，或获授权的代传人员      |
| 确认投放分配        | 投放负责人、项目 AM、管理员                   |
| 开启循环复用        | 管理员或单独的 `material.reuse.override` 权限 |
| 超送分配/撤回       | 项目 AM、投放负责人、管理员                   |

审计至少记录：操作者、时间、项目前后值、算法版本、分配批次、复用原因、撤回原因、客户端幂等键。

## 11. 非功能要求

- **幂等性**：确认、交付、发布重试必须使用幂等键。
- **并发安全**：排序、分配和发布确认使用乐观锁；唯一约束作为最终防线。
- **性能**：100 个子需求、50 位素材师、5,000 个生产名额的预览在后端 2 秒内返回。
- **可观测性**：记录均衡差值、素材重复拦截数、素材缺口、超送池停留时长和复用授权次数。
- **兼容性**：旧工单可读、可交付；进入新分配页时再按需迁移，避免一次性重写历史数据。

## 13. 关键测试场景

1. 3 条子需求数量分别为 2、3、4，分给 2 位素材师：总数应为 5/4，各子需求内差值不超过 1。
2. 已有 2 个已交付名额时新增素材师：已交付归属不变，只均分剩余名额。
3. 两位管理员同时确认不同预览：后提交者收到版本冲突，不产生重复名额。
4. 10 个投放执行单元、10 个素材版本：确认后形成 10 条唯一绑定。
5. 10 个投放执行单元、8 个素材版本：默认阻断并显示缺口 2。
6. 发布接口超时后使用同一幂等键重试：分配项和广告记录数量不增加。
7. 子需求计划 3、验收 5：超送池恰好出现 2 个版本。
8. 尝试把超送素材分给其他项目人员：后端拒绝且记录安全日志。
9. 同名素材师使用不同用户 ID：负载和交付记录分别统计，不合并。
10. 已使用超送素材执行撤回：普通撤回失败，管理员只能通过专门的纠错流程处理。

## 14. 迁移与发布建议

### 阶段一：数据与只读预览

- 增加排序、生产名额、项目成员、分配批次和使用台账。
- 旧工单按现有顺序和交付记录生成兼容映射。
- 任务中心先展示均衡和重复风险，不改变现有发布行为。

### 阶段二：生产分配与超送

- 开启生产分配确认、稳定素材师 ID 交付和超送池。
- 新工单强制走生产名额；旧工单继续兼容。

### 阶段三：投放硬去重

- 广告创建改用明确分配项。
- 先告警灰度，再切换为素材不足默认阻断。
- 保留有权限的循环复用开关作为例外流程。

回滚时只关闭新入口和硬阻断，不删除已写入的分配及审计记录。

## 15. 待产品确认

以下四项会影响最终交互和接口，建议按默认方案评审：

1. **“多个投放”的粒度**：默认按“人员 + 账户 + 广告组 + 广告位”组成执行单元；若只需按人员去重，可缩小粒度。
2. **素材不足策略**：默认硬阻断；是否允许普通负责人选择循环复用，还是仅管理员可用。
3. **同项目人员范围**：建议以正式项目成员表为准，并默认只包含 AM、投放负责人和投放执行人员；素材师是否也可作为超送接收人需确认。
4. **超送归属**：默认独占分配，不复制素材；若业务要求多人共享，需要单独定义共享素材与“禁止重复投放”的优先级。
