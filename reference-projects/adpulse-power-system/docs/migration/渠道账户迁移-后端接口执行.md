# 渠道账户迁移：后端接口执行

本版将老生产 `fbad_channel_account` 的渠道账户初始化到新测试或新生产的 `ad_account_asset`。同一套代码按服务端环境配置运行，不通过 HTTP 参数动态切换数据库。HTTP 请求只创建/启动任务，实际读取与写入由 **adpulse-main-server** 的独立后台线程执行。无需在用户电脑运行 Python 或保持接口连接。

## 环境与前置条件

|---|---|---|---|
| 来源：老生产，只读 | 54.168.180.20:3306 | fbad-suger | 668439ab-d5b1-11f0-a11e-5635bb0443e0 |
| 目标：新测试，使用测试 main 服务自身的数据源 | 172.31.23.105:3306 | adpulse_system | 16903961-99f2-11f1-a1fe-86f52840e8b4 |
| 目标：新生产，使用 main 服务自身的数据源 | 172.31.8.119:3306 | adpulse_system | 17c4f6b3-a2cc-11f1-99a8-ea697aa9ac3a |

| target-environment | 当前目标库渠道账本 | 固定渠道批次 | 老渠道 155 的目标 ID |
|---|---|---|---|
| TEST | mig_channel_prod_test_batch | mpower-prod-to-test-channels-v1 | 9900109 |
| PRODUCTION | mig_channel_prod_prod_batch | mpower-prod-to-prod-channels-v1 | 1 |

1. 所选目标环境的渠道迁移必须先完成：上表对应账本与批次为 `applied`，并保存完整渠道映射。代码从当前目标库读取，不把上表示例 ID 写死到业务逻辑中。本接口不会代为迁移渠道、修改渠道表结构或根据渠道名称推断 ID。
2. 管理员核对实例 UUID 与库名后，人工执行 `adpulse-main/src/main/resources/db/migration/V44__create_legacy_asset_migration.sql`。只建互斥、任务、明细三张迁移表；不改资产业务表。不要重复执行已成功的建表语句。
3. main 服务所在服务器必须能访问来源地址。为老库准备只读账户（只需读取 `fbad_channel_account`）；不要把连接参数或凭据传入 HTTP 请求。
4. 根据部署环境，从同目录 `application-asset-migration-test.example.yml` / `application-asset-migration-production.example.yml` **只选择一份**复制到服务器配置目录，用 `spring.config.additional-location` 追加加载。设置 `ASSET_MIGRATION_ENABLED=true`、`ASSET_MIGRATION_OPERATOR_IDS`（真实登录用户 ID）、来源 JDBC URL、用户名和密码。示例来源 URL：`jdbc:mysql://54.168.180.20:3306/fbad-suger?serverTimezone=UTC&characterEncoding=UTF-8`。实际 TLS 参数沿用部署环境的数据库连接要求。
5. 接口既要求现有 JWT/Redis 登录会话，也要求操作员在迁移白名单。启动人必须是计划创建人。后台每批检查操作员仍有效。

功能默认关闭，关闭时不注册接口、不启动工作器、不连接来源库。来源连接池独立且只读，不替换主库 DataSource/MyBatis 配置。启用时必须显式指定 `target-environment` 和 `target-uuid`，不再默认生产。只改变 Spring profile 或数据库 IP 不够，迁移环境配置也要一致。SQL 表名由 TEST/PRODUCTION 固定白名单选择，不允许自由拼接表名。

通用配置 `application-asset-migration.example.yml` 也可使用，但需额外设置 `ASSET_MIGRATION_TARGET_ENVIRONMENT` 与 `ASSET_MIGRATION_TARGET_UUID`。如果未来迁移到新的数据库实例，使用其实际 UUID；账本必须是针对该实例生成并提交的映射，不能直接复制另一环境的账本绕过校验。

## Redis 映射缓存与环境隔离

- 默认使用服务已有 `StringRedisTemplate`，不另建 Redis 连接。缓存值只包含老渠道 ID、新渠道 ID，不含账户、费率、渠道名称或连接凭据。
- Key 为 `adpulse:asset-migration:channel-map:v2:{TEST|PRODUCTION}:{版本哈希}`；版本同时绑定来源实例/库、目标实例/库、环境、渠道批次、完整账本哈希和映射哈希。因此两套环境即使共用同一 Redis，也不会命中对方的渠道映射。
- 每次预检、执行前验证和每批写入均先查询当前目标库，确认账本存在且 `applied`，比对来源/目标指纹，并在事务内持有账本共享锁。**缓存命中不能绕过数据库校验**。回滚或删除账本会停止任务，而不是继续使用缓存。
- 数据库只返回元信息和哈希；缓存未命中才额外查询完整 ID 映射。Redis 值也要与数据库映射哈希一致；损坏或旧值重新回源，重复/非法 ID 拒绝使用。映射按账本原顺序投影，避免聚合顺序变化导致哈希漂移。
- 缓存 TTL 为 10 分钟，正常使用时续期。账本更新会产生新 key，旧 key 自然过期，无需手工清空整个 Redis。
- 设置 `ASSET_MIGRATION_MAPPING_CACHE_ENABLED=false` 可关闭缓存，每次直接查数据库。缓存连接失败或没有 Redis Template 时自动回源；登录认证原有 JWT/Redis 校验不变。
- 目标渠道当前名称、有效状态与资产前镜像不缓存，每批仍查数据库并校验。任务、进度、前后镜像继续持久化在各自 MySQL，Redis 丢失不丢执行进度。

2026-09-14 只读核验：两套目标库均为 MySQL 8.4.11，ID 投影 SQL 已实际验证。测试库已有 `applied` 渠道账本，实际映射哈希校验通过；生产库尚无 `mig_channel_prod_prod_batch`，需先完成生产渠道迁移。此次核验未创建表或写入业务数据。

## 字段与冲突口径

| 目标业务字段 | 取值 |
|---|---|
| channel_id | 老 channel_id 经已提交渠道迁移账本映射后的新 ID |
| channel_name | 映射后新渠道的原始名称，保留尾部空格 |
| account_id | 老 `fb_account_id`，trim 外层空白后移除一次开头 `act_`，按字符串保留前导零 |
| account_type | 老 `account_type` 原值；本版不自行合并大小写、不添加类型配置 |
| account_attribute | 老 `whitelist_type`：1=普通户、2=准稳户、3=稳定户 |

老 `account_id` 是内部主键，只保存在审计来源记录中，不作为广告平台 ID。

- 同一规范化账户 ID、其余来源字段完全相同：合并为一个计划项，保存全部来源记录；字段不一致则整组隔离。
- 非 1～100 位 ASCII 数字的账户 ID、未知属性、目标属性配置缺失、目标多条有效资产、人工锁定记录、非空属性冲突：隔离，保留原因，不覆盖。
- 来源属性为 NULL：保留已有目标属性；新增则写 NULL。保留下来的历史属性若已不在有效配置中，执行会停止并要求处理配置。
- 目标按账户 ID 查询**全部有效记录**：0 条新增、1 条比较后更新或不变、多条隔离。不使用普通保存接口或通用 upsert。
- 没有渠道映射或渠道已删除：整批预检失败，先完成渠道迁移。
- `bm3`/`BM3` 等大小写、尚未配置的账户类型均保留来源原文，界面下拉选项可能不能直接选中；不擅自改业务字典。

已有资产仅更新渠道 ID、渠道名称、账户类型、账户属性，账户 ID 作为稳定匹配键不改变。不会清空或迁移账户名称、平台状态、BM、卡号、使用人、库存状态、人工锁定标志。数据库自动维护的 `updated_at` 可能变化。

新增行使用表默认值：`account_name=''`、`inventory_status='AVAILABLE'`、`is_manually_updated=0`。另外填写必需来源 `update_source='LEGACY_MIGRATION'` 和创建/更新人。这些是入库所需系统字段，不是额外来源业务字段。**后续飞书同步仍可以覆盖五字段资料**；本次是一次性初始化，不保证以后永久保持老系统值。启动接口要求显式接受这两个行为。

## 接口调用

默认完整前缀为 `/api/main/internal/migrations/channel-account-assets`。以下请求均携带 `Authorization: Bearer <登录令牌>`；POST JSON 使用 `Content-Type: application/json`。延续系统规范：HTTP 200 不等于成功，必须检查响应 `code`（200 成功、403 无权限、504 业务冲突、600 系统异常）。

### 0. 核对当前服务环境

```http
GET /api/main/internal/migrations/channel-account-assets/environment
```

返回环境 TEST/PRODUCTION、来源配置的 UUID/库名、已与当前目标连接核对的目标 UUID/库名、账本名称、批次和缓存开关。不会返回连接用户名或密码。此接口不要求辅助表已建；实际来源连接在预检时另行核对。

### 1. 创建异步预检

```http
POST /api/main/internal/migrations/channel-account-assets/plans
```

无请求体。返回 `data.id`（任务 UUID）和 `state=QUEUED`。此操作只写迁移任务表，后台预检只写迁移明细表，不写 `ad_account_asset`。

### 2. 查询预检/执行进度

```http
GET /api/main/internal/migrations/channel-account-assets/{id}
```

每 3～5 秒查询一次。`READY` 表示预检完成，查看 `planHash`、`sourceCount`、`total`、`isolated`、`duplicates`、`completed`、`error`。

- `total`：可执行的规范化账户数，包含无需更新的项。
- `isolated`：隔离的规范化账户分组数。
- `duplicates`：同组首条之外的来源记录数，包括被隔离的冲突分组额外记录。
- 数量关系：`sourceCount = total + isolated + duplicates`。
- `completed`：已经提交并通过五字段回读验证的账户数，包含 `UNCHANGED`。

### 3. 审阅计划与异常明细

```http
GET /api/main/internal/migrations/channel-account-assets/{id}/items?state=ISOLATED&afterId=0
GET /api/main/internal/migrations/channel-account-assets/{id}/items?state=PENDING&afterId=0
```

`state` 可省略（全部），也可为 `DONE`。每页最多 250 条；返回 `nextAfterId` 不为 null 时，把它作为下一页的 `afterId`。明细包含动作 `INSERT/UPDATE/UNCHANGED/ISOLATE`、隔离原因、全部来源记录、前镜像、目标五字段及执行后镜像。所有接口主键以字符串返回。

### 4. 启动已审阅计划

```http
POST /api/main/internal/migrations/channel-account-assets/{id}/execute
Content-Type: application/json

{
  "planHash": "填预检返回的完整哈希",
  "acceptAvailableInventory": true,
  "acceptAutomaticSync": true
}
```

返回 `VALIDATING` 后后台继续执行。执行前重新读取来源快照并比较哈希，变化则停止；之后执行固化的快照，不增量追随来源的新改动。计划同时绑定环境和账本版本，跨环境复制的计划不能继续执行。同一个任务重复请求不会重复迁移。关闭 Postman/浏览器或 HTTP 超时不会取消已入队任务，可用任务 ID 查询。

状态：`QUEUED → READY → VALIDATING → APPLYING → DONE / DONE_WITH_ISSUES`；任一步失败为 `FAILED`。`DONE_WITH_ISSUES` 仅表示可执行记录已完成，隔离记录仍未迁移。

## 性能、并发与失败处理

- 来源五字段使用一次有上限的查询获取（最多十万条），目标批量查询；250 条一批批量 INSERT/UPDATE，每批间隔 2 秒。避免用户电脑到两端数据库逐行往返。实际耗时取决于服务器网络、锁等待和数据库负载，不承诺固定速度。
- 各实例通过目标数据库互斥行串行执行迁移任务；READY 计划不占执行槽位。旧 READY 计划可以启动，但仍会进行来源、账本、目标前镜像校验。
- 每批采用 REPEATABLE READ、目标行/缺失 ID 范围锁，写入与明细完成状态、进度一起提交；读取所有活跃匹配项，不依赖 `(account_id,account_name,deleted_at)` 唯一键来判断账户唯一性。
- 每批核对实例、渠道账本及渠道原名，锁定目标后比较前镜像（包括修改时间、人工锁定标志）。发现计划后目标被编辑、同步更新、新增或删除，则当前批回滚，不覆盖这些变更。
- 成功批次已经提交，任务失败**不会全量回滚此前批次**。原有计划与前后镜像保留；处理冲突后重新建计划，已一致的账户会成为 `UNCHANGED`。不提供未经关联检查的自动删除/全量回滚接口。
- 进程重启后，未提交事务回滚；`QUEUED/VALIDATING/APPLYING` 任务从持久化状态继续。`FAILED` 不自动反复重试。主动关闭功能后任务暂停，重新打开会继续未完成状态。
- 如飞书/Mongo 同步持续更新目标修改时间，可能频繁触发前镜像冲突。正式执行宜安排安静窗口、暂停相关写任务；本接口不擅自修改现有同步任务或渠道名称 trim 逻辑。
- 各环境渠道迁移的既有回滚检查已涉及渠道引用；资产迁移后不要直接回滚渠道或删除迁移账本。

## 从上一版升级

### 预检返回 IllegalArgumentException 的配置排查

若 `state=FAILED`、`planHash=null` 且错误只有 `IllegalArgumentException`，先检查老库来源配置。已复现：`source-url` 为 `${ASSET_MIGRATION_SOURCE_URL:}` 且服务器没有该变量时，Hikari 会因 JDBC URL 为空抛出此异常。`DB_URL/DB_USERNAME/DB_PASSWORD` 只用于新库，不能替代迁移专用的三个来源变量。

可以在所选 `application-test.yml` / `application-prod.yml` 的 `adpulse.asset-migration` 下直接填写 `source-url`、`source-username`、`source-password`，或分别配置 `ASSET_MIGRATION_SOURCE_URL`、`ASSET_MIGRATION_SOURCE_USERNAME`、`ASSET_MIGRATION_SOURCE_PASSWORD`。不要将这些变量的值输出到日志或接口响应。

新版在创建预检前校验这三项；旧任务执行到来源读取时也有校验，会返回具体缺失的配置项。其他异常记录阶段、根因类型和代码位置，不记录原始异常 message。已 FAILED 的任务不会自动恢复，补齐配置并重启后重新 `POST /plans` 获取新任务 ID；无需删除旧任务或修改其状态。

本次没有增加迁移表字段，已有三张辅助表的环境不重复执行 V44。部署前补充显式环境和 UUID 配置。旧版 READY 计划需要重新预检；旧版待执行任务的渠道哈希与新版不同，重启后会安全停止，不能把生产任务复制到测试库续跑。若已有部分批次提交，保留账本和明细，新预检会按目标实际值识别无需更新的项。

入口：渠道管理页面的操作菜单 →「渠道与账户同步」。前后端需同时发布；页面首次打开调用 environment 接口核对实际目标实例，未确认环境或无迁移权限时不能执行。前端不传数据库地址，也不能切换 TEST/PRODUCTION。

5. 账户任务处于 QUEUED/VALIDATING/APPLYING 时，后端禁止新增渠道迁移批次；先等待任务结束。渠道同步后，旧 READY 账户计划应重新预检，避免映射版本变化导致失败。
