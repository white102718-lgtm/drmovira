## 完整合同与正文补充

原始活动合同为UserWrite、TeamWrite、RoleWrite及其读对象、游标页面；原文件保持不变。正文要求恢复手机号联系方式和身份状态，原User Schema未列出，单独登记于`extensions/system-identity-fields.json`。

- 用户：姓名1—50、昵称0—50、规范邮箱3—254、手机号0—32、团队UUID、1—20个功能角色、数据角色、0—500个明确管理团队及INVITED/ENABLED/DISABLED状态。手机号不是短信验证或身份认证证明。
- 团队：名称1—100、ENABLED/DISABLED状态；不借用若依部门树推断管理授权。
- 角色：名称1—50、0—100个菜单代码、0—500个动作；只允许当前注册表中的八个业务菜单和保留动作，不恢复退役申请/审批等权限，不接受若依通配符。
- 功能角色按并集计算，不能要求同一角色同时包含菜单和动作；数据范围仍须额外求交。UUID集合规范化后判重，不因大小写获得重复授权。
- 普通用户不能带团队管理范围；TEAM_ADMIN允许明确空集合，不会因此自动获得所在团队全部资源。
- 写入未知字段、重复JSON属性、伪造tenant/actor/id/revision/identity_status和密码都拒绝。身份是否验证只由后端可信认证流程决定。

列表须先校验system菜单与对应manage动作，再按当前数据角色筛选；游标绑定筛选、读取水位、当前授权与目录版本。新写入、版本、幂等结果、审计及outbox同事务，不在事务里发送邀请邮件。
