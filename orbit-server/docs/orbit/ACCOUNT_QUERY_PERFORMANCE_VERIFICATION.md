## 实际问题与改动

首次当前基线 44/44 通过，但 200 行逐页期间的实际 `EXPLAIN FOR CONNECTION` 显示：事实表按 tenant 读取约 49 万估计行，再 hash join 当前页 JSON_TABLE。该观察保存在主线 runtime，基线回执为 `python-account-scope-capacity-current040-baseline.json`。20 行并发达标不能覆盖这个大页执行计划问题。

聚合改为当前页账户驱动的 STRAIGHT_JOIN，并使用事实表既有 `(tenant_id,account_id,business_date)` 主键。日期区间、冻结归属权限、Decimal 金额及完整/未知口径保持原查询条件。250 页完整账户对账阶段从基线约 441 秒缩短到首轮约 15 秒；最终整轮该阶段约 26 秒，保留实测波动，不只挑最快一轮。

并发检查扩展到 20/50/100/200 四档，每档 20 线程各 10 次，共 800 次；失败样本不能剔除。首轮 200 行 P95 为 1.257 秒，超过原 1 秒目标，回执与测量分别保存在 `python-account-capacity-optimized-failed-01-four-sizes*.json`。

后续检查确认扩展 DTO 已是严格 JSON 值，Money/UUID/时间都已转换为字符串。仅该只读大页入口直接生成 JSONResponse，省去 FastAPI 对约 49 万字节嵌套 DTO 的重复递归转换。形状微测中两条路径 JSON 字节完全一致；它只用于定位 CPU 开销，不作为业务或并发证明。原会话、实时权限、事务及安全响应头继续由现有入口和中间件验证。
