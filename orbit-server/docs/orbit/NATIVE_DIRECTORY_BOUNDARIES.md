# 原人员与角色目录边界

本文件描述Python框架内的原菜单兼容，不替代ORBIT人员/团队/角色合同，也不代表SYS整体验收。最新结构化结果见evidence/python-framework-integration.json；Java回执不继承。

## 读取与权限

| 原入口 | 实时业务授权与对象范围 | 处理方式 |
| --- | --- | --- |
| `/system/user/list`及原人员导出 | 原系统动作/部门范围，加system.users.manage；当前租户，USER本人，TEAM_ADMIN本人及显式管理团队，SUPER_ADMIN当前租户 | SQL在COUNT和分页前相交；SUPER可保留未映射技术账号维护；原技术账号只能读未映射技术集合 |
| `/system/user/{id}`、`/system/user/authRole/{id}` | 与上相同；不因原通配权限扩大租户范围 | 不可见404；旧的跨租户已分配角色关系409待整理，不泄露其角色名称 |
| `/system/role/list`及原角色导出 | 原动作/部门范围，加SUPER_ADMIN与system.roles.manage | SQL在COUNT和分页前过滤其他租户已映射角色；原技术角色不伪造业务租户 |
| `/system/role/{id}`、`/system/role/deptTree/{id}`、`/system/menu/roleMenuTreeselect/{id}` | 上述角色授权与可见角色对象 | 不可见404；菜单树的旧无额外动作装饰器不能绕过业务动作 |
| `/system/role/authUser/allocatedList`与`unallocatedList` | 角色对象/动作与人员动作/范围同时满足 | 选择器同样先过滤候选再COUNT/分页；缓存命中也重新检查两个动作 |
| `/system/user/profile` | 原本人认证及资料自服务；不代替管理员授权 | 普通资料不覆盖登录时缓存的角色/岗位；管理授权和安全事件另行复核 |

只读回显已分配的停用角色，不会使该角色重新参与认证。管理详情和认证查询分离；已分配停用选项带原status，前端禁选并保留既有引用。普通人员/团队管理员不通过资料读取枚举所有可授予角色。业务角色定义仍在ORBIT角色页维护，基础角色只读和复制规则不变。

## 缓存与序列化

- 原缓存扩展在Redis读取前运行。原人员目录重核人员动作；原角色目录及授权树重核角色动作；人员选择器额外重核人员动作。
- 键同时绑定认证版本、当前租户/数据角色、当前人员版本/团队与目录时钟，保留原请求/筛选/时区维度；不使用浏览器tenant或actor参数。
- 同键命中后降级、撤回动作、目录更新及撤管需要拒绝或重新读取。未映射技术账号的原目录暂不缓存，因为其可见集合受全局映射变化影响；这不是容量优化结果。
- 原人员列表和成员列表不能序列化password，连password:null也不输出；不因API缓存而保存该字段到响应缓存。
- 原路由业务拒绝保留code/msg形状并返回实际403/404/409；不读取只有/api/v1中间件才创建的request_id。原认证兼容错误包保持原行为。

## 原表单与业务字段

- 原编辑页的昵称50个NFC Unicode码点、邮箱254、联系方式32；不再由旧HTML长度或国内11位正则截断。编辑资料不发送空密码；修改密码继续走专用已授权入口。
- 已映射业务人员的联系方式可重复，与新User API一致；原本人资料与原完整表单均按稳定人员/身份ID更新，不合并、覆盖其他同联系方式身份。邮箱/手机号不作为OIDC身份验证。
- 原未映射技术账号保持原框架联系方式唯一检查；登录用户名仍是原系统的独立标识，不通过联系方式查找或合并业务身份。
- 原详情不能漏掉已分配停用角色，不能因编辑基础资料而清掉其关联；资料变更不能修改密码或推进无关认证版本。
- 普通资料、角色分配及安全事件的事务桥接详见PYTHON_IDENTITY.md。上述读取不授予额外写权限；原接口不凭空增加幂等/CAS成功保证。

- 原人员删除/更新式导入整批排除业务及历史映射，纯技术流程保留，已有实际专项；其余未列出的批量异常和并发仍待覆盖。

- 可选原当前用户缓存启用后的跨入口授权失效；当前默认关闭该快照缓存，接口响应缓存另有实际命中专项。
