# 规则拥有者与团队授权

## 显式身份目录

V006建立orbit_business_team、orbit_business_user、orbit_business_team_manager。业务用户UUID映射若依sys_user数字ID，业务团队UUID独立于dept_id；同租户登录用户只映射一个业务身份，用户和团队均有enabled/revision，管理团队有显式enabled/revision授权。跨租户团队引用由复合外键约束，不以部门树或若依管理员名称推断数据权限。

空库仅承接V001已显式绑定到默认租户的启用用户1，新增默认团队及其业务UUID映射。不批量授予其他若依用户，不自动建立TEAM_ADMIN管理授权，不覆盖已有映射。身份维护UI、受控授撤权及最后一名超级管理员保护尚未实现，本迁移不代表人员团队管理模块完成。

## 规则内部写入复核

RuleDraftStore在同一事务内查询当前启用租户、若依用户状态/软删除、当前orbit_user_scope、启用业务身份及其当前团队；不信任会话中旧数据角色。共享锁与正文/事件/幂等写事务一起持有。登录用户没有业务UUID映射时拒绝，不因存在sys_user记录或部门而放行。

USER只能操作owner_user_id等于自己业务UUID的规则；TEAM_ADMIN只可操作显式管理团队内的规则，属于某团队不隐含管理该团队；SUPER_ADMIN限当前明确租户上下文内的规则。当前未实现受控X-Target-Tenant/server_scope切换，不能借传入另一个tenant绕过当前上下文。当前身份整体失效403，范围外规则或跨租户对象404。

编辑先按当前头的冻结ownership复核权限，再检查新ownership，不能把他人规则的owner改成自己来夺取。新分配要求owner存在、业务身份启用、若依用户有效、当前租户授权有效、当前成员团队与请求团队相同且团队启用。不存在/不可见引用404；已获权但成员关系/状态不可用422。

存量资源按正文冻结的owner_user_id和owner_team_id授权。成员换队不会把旧规则自动移给新团队；原团队管理者仍可归档其冻结归属的旧规则，新分配必须核验当前成员关系。USER的“本人”按owner_user_id判断，不能把团队判断取代用户所有权。

幂等重放重新读取当前身份和当前规则头的ownership，再返回首次成功的不可变版本。规则被重新分配、管理团队被撤销、用户停用/软删除、业务身份或团队停用、数据角色撤销/非法时，旧幂等键不能恢复已经失去的数据访问权。

## 证据与边界

真实MySQL专项新增8项：USER不能替同团队他人创建/改归属夺取、TEAM_ADMIN须显式授权且撤权后重放拒绝、不能管理其他团队而本租户SUPER_ADMIN可用、六种当前身份撤销状态重放拒绝、新分配成员关系/状态验证、成员换队保留冻结归属、改owner后旧USER重放拒绝、缺UUID映射不能从若依部门推断授权。总专项33项，见evidence/mysql-configuration-integration.json。

首轮33项有1项跨租户错误码回归：新增身份检查错误返回403，原合同及测试要求范围外对象404。修正服务端上下文分流，原断言未改；失败回执归档，修复后33项通过。并发授权撤销的完整时序、公开HTTP安全链仍未逐项验收，不能据共享锁实现就宣称这些验收完成。

当前仍无规则公共HTTP入口、登录/menu/action交集、scope-snapshot与profile可信来源、真实模拟及可启用闭环。内部方法仍由可信服务端调用方提供actor，不能直接绑定前端actor字段。reference_status继续PENDING_REFERENCES，不启动Worker、不调用模型、不执行广告写入。人员团队管理、跨模块完整权限与规则页面均未完成，不增加完整业务勾选。
