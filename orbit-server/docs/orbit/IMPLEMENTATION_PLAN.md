## 四、数据库与查询性能设计

逐模块表/访问路径/索引及实测状态见[数据库设计与性能台账](DATABASE_DESIGN.md)。

- 主数据/配置/授权/任务状态与大规模统计事实分开设计。事务主库MySQL；Redis不是唯一业务存储，外部文件在对象存储，数据库保存元数据和hash。
- 每张业务表显式tenant；复合索引优先匹配实际tenant/owner/status/date筛选和稳定排序。关联批量读取，避免逐行N+1；不对大表无条件COUNT/SELECT *或无限聚合。
- 业务UUID和外部平台ID在API始终字符串；金额使用Python Decimal与MySQL DECIMAL/十进制字符串，禁止float累计或跨币种混加；DATETIME(3)按UTC，账户业务日按IANA时区。
- 列表20/50/100/200采用keyset游标，绑定筛选、排序、数据水位和权限版本。未知null后置、ID第二排序；不以深OFFSET代替游标。
- 事实表按时间组织，分区键、唯一键、幂等与归档一起设计；索引/分区须以执行计划证明有效。汇总按可追踪水位增量更新，迟到/重复数据可重算对账。
- 报表与在线事务解耦；先使用日/小时汇总。列式分析库保留读取适配边界，是否启用以真实瓶颈决定，不提前声称已具备。
- 同步、导入、AI、导出为有界后台任务，持久状态/进度/取消/重试；导出分批流式读取，不能一次加载全部数据。
- 业务写、版本、幂等结果、审计、outbox同事务；消费者以事件ID去重。锁顺序固定，事务内不等待AI或平台网络调用。
- 权限在每次请求、任务发送、回读/下载时复验；缓存键包含租户/身份/数据角色/scope和数据版本，撤权不能等待TTL。

模块设计记录必须包含：表/字段/唯一约束、访问路径、复合索引及选择原因、数据水位/聚合、归档保留和预期容量；SQL中文COMMENT和数据字典一致。

### 当前执行调整：先交付业务闭环（2026-11-09）

#### 1. 以可操作流程组织开发，不以内部组件组织交付

- 主线同时只推进一个主要业务闭环。每个闭环开始前列明页面入口、用户操作、字段逻辑、弹窗/二级页、接口、数据库、权限、异常及验收证据；所有原需求保留，不把大功能拆成大量“完成项”制造进度。
- 优先收口当前已有页面和后端的规则定义流程：列表、详情、新增、编辑、范围选择、保存回读及暂停/归档，逐项核对原合同与实际缺口。模拟、启用、调度单独登记依赖，不借前者通过宣称整个规则模块完成。
- 完成这一闭环后，从账户、渠道、素材的交付差距表选择最接近完整交付的一项收口，再按投放/模板/任务、监测、规则模拟与AI的真实依赖推进。不得仅因底层方案更容易继续扩写，就不断新增内部协议而推迟已有页面交付。
